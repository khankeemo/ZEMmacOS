# Websmith Digital SDK — Integration Guide

> This guide is the source-of-truth copy shipped inside generated **Python** SDKs
> (template path: `app/internal/publisher/template/python/Integrations.md`). The same
> concepts apply across all runtime kits generated by the Websmith Universal License
> Platform.

## 1. Introduction

The Websmith Digital SDK enforces licensing inside your application. It manages license
validation, hardware binding, trials, activation, renewal, reactivation, support/sales
communication, and notifications. It is generated per product by the Websmith SDK
Publisher and configured through a single `api-config.json` file.

**Architecture hierarchy**: Master Implementation Document → Language Templates → SDK
Publisher → **Generated SDK**. The generated SDK is *output only* — do not edit it;
regenerate with the SDK Publisher for any change.

## 2. Install

1. Download the generated SDK ZIP
   (`WSD_SDKToolkit_<Product>.zip`) from your Websmith portal.
2. Unzip it into your project (e.g. under `sdk/`).
3. The SDK is pure Python — no third-party dependencies (stdlib only:
   `datetime`, `json`, `os`, `sys`, `platform`, `tkinter`, …).

```
sdk/
  __init__.py
  license_engine.py        # license validation + decision engine
  universal_license_center.py  # customer-facing license UI (ULC)
  universal_email_dialog.py    # one email dialog for all request types
  activation.py  renewal.py  trial.py  reactivation.py
  sales.py  support.py  communication.py  notifications.py
  client.py                # HMAC-signed API client
  hardware.py  crypto.py  cache.py  validation.py  live_log.py
  single_instance.py  config.py
  welcome.py
  universal_success_dialog.py  universal_restart_dialog.py
  assets/  config/  docs/
```

## 3. Configuration

Configuration is loaded from `api-config.json` (or environment variables). It is
injected by the SDK Publisher — never hardcode it.

**Product configuration**

| Key | Description |
|---|---|
| `product_id` | Product identifier (must match the platform). |
| `api_url` / `api_key` | Backend base URL (`NEXT_PUBLIC_API_URL`) and your API key. |
| `store_url` | Public store URL for checkout links. |
| `trial` | `enabled`, `duration_days`, requirements, conversion settings. |

**License & UI configuration**

- Hardware binding (`hardware_binding`), `max_devices`, `offline_days`,
  `cache_days`, `renewal_reminder_days`.
- Branding: colors, company name, support/sales email addresses, logo.
- Feature flags (trial, hardware binding, offline grace, etc.).

**Loading order**: local file/`api-config.json` → environment variable overrides →
per-product validation. Invalid configuration fails fast at startup.

> **Version synchronization**: SDK version, product version, runtime version, and the
> generated SDK version must all match. A mismatch causes generation to fail.

## 4. Quick start

```python
from sdk.license_engine import LicenseEngine
from sdk.universal_license_center import UniversalLicenseCenter

# 1. Initialize the license engine (runs the decision engine once at startup)
engine = LicenseEngine(config_path="sdk/config/api-config.json")
status = engine.initialize()

# 2. Create + show the license center (pure display; does NOT re-run the engine)
ulc = UniversalLicenseCenter(config_path="sdk/config/api-config.json")
result = ulc.show()

if result.get("action") == "launch":
    print("Application unlocked — starting main app.")
    launch_application()
else:
    print("Licensing not satisfied — app remains locked.")
    sys.exit(0)
```

## 5. Core components

### LicenseEngine
The decision engine: initialization, validation, and state management. Runs exactly
**once** during startup. Handles activation, renewal, trial, hardware binding, offline
grace, and caching through a unified interface. It never computes license/plan/days/
validity locally beyond absent-optional fallbacks — the backend
`GET /internal/backend/license/status` is the single source of truth.

### HardwareDetector
Fingerprints the system (CPU, motherboard, OS) for license binding. Hardware binding is
**permanent**; a hardware mismatch invalidates only the cached status and surfaces
"Hardware replacement requires administrator approval."

### CacheManager
Local persistence for offline support and message queuing. Stores license status,
hardware ID, and queued communications with **TTL-based expiration** for the offline
grace period.

### UniversalLicenseCenter (ULC)
The primary customer-facing dialog: dashboard, license status display, workflow
buttons (trial, activate, renew, request), and integration with all backend services.
The ULC is display-only; all business logic lives in the decision engine / backend.

### UniversalEmailDialog (UED)
The single email component for every request category (support, sales, activation,
renewal, reactivation, general). Auto-populates customer/ product/plan/license key/
hardware ID, supports attachments (max 5, 10 MB each; images, PDF, files) via a rich
text editor, and validates input universally.

### UniversalSuccessDialog / UniversalRestartDialog
- **Success**: shown after successful trial/activation/renewal with a summary.
- **Restart**: the merged restart workflow — save state → flush cache → close dialogs →
  relaunch the process → exit. No orphan processes or background threads may survive.

## 6. Workflows

### Trial
1. Customer registers (name, email, mobile) → OTP email verification.
2. Trial license created → bound to `hardware_id`.
3. Customer gains trial access; auto-convert to paid runs when configured after expiry.

**Endpoints**:
- `POST /api/v1/auth/otp/send` — send OTP.
- `POST /api/v1/auth/otp/verify` — verify OTP.
- `POST /api/v1/trial` — action `start` / `status` / `convert`.

### Activation
1. Customer enters license key → validation.
2. OTP sent to the registered email → OTP verified.
3. Hardware validated → license activated and bound.
4. **Success dialog** shown with restart option.

Fresh activation **clears the old cached license state** (license/plan/customer/expiry/
activation), preserves only `hardware_id` and the offline queue, then reloads live status
from the backend.

**Endpoints**:
- `POST /api/v1/license` — actions `validate`, `activate`, `deactivate`, `renew`.
- `GET /internal/backend/license/status?hardware_id=...` — live status refresh.

### Renewal
1. `POST /api/v1/license/verify-renewal` — eligibility check.
2. `POST /api/v1/license/available-plans` — list available plans.
3. `POST /api/v1/license` action `renew` — extend expiry (+ `renewal_history`).

### Reactivation / device replacement
1. Customer requests license transfer.
2. Old/new hardware validated (approval flow).
3. License bound to the new hardware; customer notified.

**Endpoints**:
- `POST /api/v1/reactivations` — request reactivation.
- `POST /api/v1/device` — actions `bind`, `reset`, `replace`.

### Requests & communication
Use the UniversalEmailDialog for `BUY`, `RENEW`, `SUPPORT`, `ACTIVATION`,
`DEVICE_REPLACEMENT`, `HARDWARE`, `GENERAL`.

- `POST /api/v1/request` — create a universal request.
- `POST /api/v1/communication/create`, `.../[id]/reply`, `.../[id]/attach` — conversation.

## 7. API reference (used by this SDK)

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/license` | `validate` / `activate` / `deactivate` / `renew`. |
| GET | `/internal/backend/license/status` | Live license status (single source of truth). |
| POST | `/api/v1/trial` | `start` / `status` / `convert`. |
| POST | `/api/v1/device` | `bind` / `reset` / `replace`. |
| POST | `/api/v1/auth/otp/send` | Send OTP. |
| POST | `/api/v1/auth/otp/verify` | Verify OTP. |
| POST | `/api/v1/license/verify-renewal` | Renewal eligibility. |
| POST | `/api/v1/license/available-plans` | Available renewal plans. |
| POST | `/api/v1/reactivations` | Request reactivation. |
| POST | `/api/v1/request` | Universal request. |
| POST | `/api/v1/communication/create` | Create conversation. |

Protected endpoints use `X-API-Key` (and HMAC signatures). Signatures use
`X-Timestamp`, `X-Nonce`, `X-Signature` with a 5-minute timestamp window and nonce
replay protection. The SDK's `client.py` handles this automatically.

## 8. Error handling

All errors follow the platform error-handling rules:

- **User-friendly messages**: no technical details exposed to the customer.
- **Specific error codes**: machine-readable codes for programmatic handling.
- **Graceful degradation**: non-critical failures do not stop operations.
- **Logging**: every user-visible message is also written to the shared `LiveLog`;
  UI and LiveLog stay in sync.
- **Rule 5 (verbatim)**: pass through real server messages; never substitute a generic
  local string for a server-provided message.
- **Rule 8 (errors)**: errors explain *what / why / next*; avoid bare
  "Error"/"Failed"/"Unknown".
- **Rule 6 (progress)**: show a live "working…" state for operations that take >1 s.

## 9. Best practices

- Initialize the decision engine **once** at startup; let the ULC consume the result.
- Treat the backend as the source of truth; never derive validity locally.
- Keep `api-config.json` injected and validated; never hardcode vendor values.
- Test offline grace and cache TTL behavior before shipping.
- Regenerate the SDK via the Publisher for any template change.

## 10. Troubleshooting

| Symptom | Likely cause / next step |
|---|---|
| Custom network unaffected, app stays locked | Initialize the engine at startup; check `api_url`/`api_key`. |
| "Hardware replacement requires administrator approval" | Hardware changed; request reactivation (Rule 2). |
| Stale status after trial/activation | Cache TTL or stale `license_status`; reload live status from the backend. |
| OTP not arriving | Check OTP endpoint + email routing; verify `otp_verifications`. |
| Version mismatch error at generation | Ensure SDK/product/runtime/generated versions are synchronized. |

## 11. Migration

To upgrade an existing integration:

1. Regenerate a fresh SDK for your product + runtime.
2. Diff `api-config.json` and re-apply your product values.
3. Review workflow changes between versions (this guide is updated in lockstep with the
   template).
4. Re-run the platform's end-to-end validation scenarios (AWS-01 Rule 10) before release.
